01 · Motivation

Why a programmer should learn chip design

For decades, software got faster for free: each new process node gave more transistors and higher clock speeds at the same power. That stopped around the mid-2000s, when Dennard scaling broke down and clock frequencies flattened. Performance gains since then come mostly from parallelism and specialization: GPUs, TPUs, video codecs, crypto engines and FPGA accelerators.

Specialized hardware is designed, not compiled from a general-purpose program. The people who understand the workload best, the software engineers, usually can't build it. Closing that gap is the theme of the DAC 62 keynote Democratize Chip Design, and the reason this course exists.

What a chip actually is

A chip is a slab of silicon a few millimetres to a few centimetres across, covered in transistors: tiny switches that turn on or off depending on a voltage. Wires stacked in a dozen or more metal layers above the transistors connect them into gates, gates into adders and memories, and those into processors. Everything a computer does, including running your Python, comes down to these switches changing state in step with a clock.

Software never "runs" in any physical sense. A compiler turns it into bit patterns, and those patterns steer which switches open and close on each clock tick. The examples below follow that path for four kinds of hardware.

208 billiontransistors in NVIDIA's B200 GPU, split across two dies. A small microcontroller has thousands of times fewer.
1 nsper clock cycle at 1 GHz. A 4 GHz CPU core starts a new cycle every 0.25 ns.
~30 cmis how far light travels in 1 ns. Signals on a chip are slower, so wire length is a real design limit.
"3 nm"is a marketing name for a process generation. No feature on a modern chip is literally 3 nm wide.
01 · Worked examples

How software ends up running on silicon

Four examples, each one level closer to the hardware. Together they show the two ways software meets silicon: a processor interprets your program one instruction at a time, while custom hardware turns your program into the circuit itself.

Example 1 · processor

One line of C on a RISC-V CPU

Start with the smallest possible program. Suppose a, b and c are integers the compiler has placed in registers x1, x2 and x3.

// C source
c = a + b;

# RISC-V assembly from the compiler
add  x3, x1, x2

# 32-bit machine code in memory
0x002081B3

The CPU never sees the letters add. It sees the 32 bits in Fig 1.1. Each group of bits is wired directly to part of the hardware: the opcode bits drive the decoder, the register numbers select register file entries, and the function bits tell the ALU to add rather than subtract.

Now follow that instruction through a classic 5-stage pipeline. Step through it to see what each stage does, down to the transistors inside the adder.

Example 2 · same code, four machines

A vector add on a CPU, a GPU, an FPGA and an ASIC

// add two arrays of 1,024 floats
for (int i = 0; i < 1024; i++)
    c[i] = a[i] + b[i];

The program is identical in every case. What changes is how much of the work is spent deciding what to do (fetching and decoding instructions, scheduling) versus doing it (the add itself). Pick a machine. The timelines are schematic, to show the shape of the work rather than real cycle counts.

Example 3 · custom hardware

Blinking an LED on an FPGA board

This is the "hello world" of hardware, and it shows the big difference from software. Nothing executes here. The code describes a 27-bit counter wired to an LED, and synthesis builds exactly that circuit from the FPGA's flip-flops and lookup tables.

module blinky (
  input  wire clk,      // 100 MHz board oscillator
  output wire led
);
  reg [26:0] count = 0;
  always @(posedge clk)
    count <= count + 1;    // adds 1 every 10 ns
  assign led = count[26]; // top bit drives the LED pin
endmodule

Bit 26 of a counter flips every 226 clock cycles. At 100 MHz that is 226 × 10 ns ≈ 0.67 s, so the LED blinks with a period of about 1.34 s. A constraints file maps clk and led to physical pins on the board, which is how the design reaches the outside world.

Example 4 · accelerator

A neural-network layer on a matrix engine

# PyTorch
y = torch.relu(x @ W + b)   # x: 1×256, W: 256×256

This line is 65,536 multiply-adds. On a CPU each one goes through fetch, decode and the register file. A matrix accelerator such as a TPU-style systolic array (Fig 13 in Section 05) loads W into a grid of multiply-add cells once. It then streams x through so that every cell does useful arithmetic on every cycle.

A framework compiler (for example XLA, or PyTorch's export path into MLIR) breaks the model into these matrix operations and maps them onto the engine. That is the same path ChipDesignAgent aims to automate for new kinds of kernels (Section 07).

Thinking in hardware: pipelining, unrolling, and patterns

In software a loop runs one iteration after another. In hardware you choose how many iterations overlap (pipelining) and how many copies of the body exist (unrolling). The initiation interval (II) is how many cycles pass before the next iteration can start. Move the sliders.

06 · Course elements

A 14-week course plan

The plan assumes a CS student who knows C and data structures, plus some computer organization. It moves from gates to accelerators, then to the AI-assisted flow covered in Section 07. Filter by track, and tick off modules as you finish them (saved in this browser only).

Assessment (suggested weights)

Labs 40%
Project 35%
Midterm 15%
Quiz 10%

Labs are weekly and graded by passing testbenches. The final project is team-based: an accelerator taken through verification and either FPGA deployment or an open-source ASIC flow, with a short report comparing speed and resources to a CPU baseline.

Capstone project ideas

  • GEMM accelerator in HLS, with a measured speed-up against the CPU
  • Image-filter pipeline (blur → Sobel) using line buffers and dataflow
  • Small RV32I core that runs a C program on an FPGA board
  • A design small enough for an educational shuttle tapeout (e.g. Tiny Tapeout)
  • Extend ChipDesignAgent with a new pattern or a cost model (Section 07)

06 · Lab hardware

Devices, boards and equipment: from breadboard to silicon

Students should hold the hardware in their hands at every stage. They wire real logic chips before writing Verilog, program a board before using the cloud, and finish by sending a design to a chip shuttle. The plan below lists what a lab needs at each stage, with an open-source option and a vendor-tool option where both exist.

Why each instrument is there

  • Multimeter: check supply voltages and continuity before powering a breadboard. It is the first debugging tool.
  • Bench power supply with current limiting, so a wiring mistake trips a limit instead of burning a chip.
  • USB logic analyzer (8–16 channels): watch counters, state machines and serial protocols on real pins. Open-source PulseView (sigrok) decodes UART, SPI and I²C.
  • Oscilloscope (2–4 channels, 100 MHz or more): see that a "digital" signal is really analog, measure rise times, and connect timing analysis (Fig 8) to reality.
  • ESD mat and wrist strap: FPGA boards and bare chips are sensitive to static.
  • Soldering station shared between benches, for headers, PMOD adapters and the chip-carrier board in the silicon stage.

Kit planner

Set the class size and the toolchain to get a parts list with quantities. Per-student items include 10% spares. Benches are shared by two students and project teams have four. Cost tiers are approximate prices per unit in USD: $ under 50, $$ 50–400, $$$ 400–2,000, $$$$ over 2,000. Check current supplier prices and academic discounts before ordering.

The silicon stage

A full custom chip is out of reach for a course budget. A shared multi-project shuttle is not. Many designs are combined on one die and fabricated together, so each team pays for a small tile instead of a whole wafer.

  • Tiny Tapeout: an educational program that puts hundreds of small digital designs on one chip using open PDKs. Each design gets a tile with a handful of I/O pins, and the chip ships on a carrier board that selects which design is active.
  • Academic multi-project wafer (MPW) services such as Europractice in Europe give universities access to commercial processes for larger designs, with longer lead times and NDAs.
  • Open PDKs (SkyWater SKY130, GlobalFoundries GF180MCU, IHP SG13G2) let students run the full flow in Section 04 without signing an NDA.

Bring-up: testing the chip you made

  • Plug the carrier board into a bench PC and select your design.
  • Drive inputs from a microcontroller (for example a Pico 2) and capture outputs with the logic analyzer.
  • Re-run the same cocotb tests from Module 5 against the real chip and compare with simulation.
  • Use the oscilloscope to find the highest clock speed at which the design still works, then compare it with the static timing estimate from the flow.
  • Write up the differences between simulation and silicon. This is the most valuable report students produce.

Computers and infrastructure

Bench PCsLinux, 8+ cores, 32 GB RAM, 200 GB free disk. Vivado and the OpenROAD flow are memory-hungry, and 16 GB machines struggle with larger designs.
Agent serverTo run ChipDesignAgent locally for a class, use one shared machine with a GPU. Gemma 4 alone needs about 10 GB, and on CPU a single run takes many minutes.
LicensesThe free editions of Vivado and Quartus cover the entry boards listed above. Commercial ASIC tools need a university program agreement; the open-source track needs none.
Cloud creditsUse them for regressions, larger HLS builds and AWS F2 runs (Section 08) instead of buying data-center FPGA cards.
07 · Case study

ChipDesignAgent: automating the path from code to accelerator

Sections 02–05 describe what a hardware engineer does by hand: profile the code, recognize the computation pattern, restructure it for hardware, and check it still gives the same answers. The keynote's "agentic approach" gives each of those jobs to an AI agent, coordinated by an orchestrator. ChipDesignAgent is a working version of that design, built on Google's Agent Development Kit (ADK) and running a local Gemma 4 model through Ollama. Click a box to see what that agent does and which week of the course it automates.

One run, step by step: a 64×64 matrix multiply

The tool outputs below are what the project's tools return on examples/gemm.c, checked by its test suite. In a live run, Gemma 4 decides the order of calls and writes the HLS code itself, so its wording and code will differ from run to run.

What the design gets right

  • The LLM does the flexible work. Rewriting arbitrary code and deciding what to try next are things a rule-based compiler can't do.
  • Proven tools do the parts that need guarantees. Pattern detection, lint and systolic-array generation are deterministic, and the LLM calls them instead of guessing.
  • Verification closes the loop. Each candidate runs against the original code on random inputs. In the tests, an off-by-one bug in the k loop is caught immediately.
  • It runs locally. Gemma 4 runs on Ollama, so the code never leaves the machine, which matters for proprietary designs.

Where it falls short today

  • C/C++ input only. The PyTorch and MLIR front ends shown on the slide are not built yet.
  • Correct but not measured. Without Vitis HLS installed there is no latency or resource feedback, so the loop stops at "passes simulation", not "is fast".
  • Shallow analysis. The profiler is a lightweight parser, not a compiler front end. It handles counted loop nests but not pointer aliasing or complex control flow.
  • Small-model reliability. A local model can misformat tool calls or stop early. The orchestrator caps retries, but results vary from run to run.
  • External optimizers need setup. AutoSA needs Linux or WSL; HARP, Prometheus and LIFT are research code without a standard command-line interface.

Using it in the course

  • Week 11 lab: write the GEMM accelerator by hand first, then compare it with the agent's version and explain the differences in pragmas and code structure.
  • Week 14 lab: add a convolution pattern to the profiler's pattern matcher and a test for it.
  • Project: build an analytical latency estimator (the Section 05 formula applied to each loop nest), so the agent can compare candidates by speed as well as correctness.
  • Experiment: run the same kernels with Gemma 4 and a larger model, and measure how often each produces a design that passes simulation.

Discussion questions

  1. The verification agent compares outputs with a relative tolerance of 10⁻⁴. Why is exact equality the wrong test once the HLS version reorders a floating-point sum? When would you require bit-exact results?
  2. Passing random-input C-simulation does not prove equivalence. What could a formal tool or targeted corner-case inputs catch that this misses?
  3. Which decisions in Fig 15 should stay deterministic and which should an LLM make? Where would you put a human in the loop?
  4. If an LLM writes RTL that ships in a chip, who is responsible for a bug found after tapeout? How does this change review practices?
  5. Does making chip design accessible to programmers mainly need better models, better tools, or better abstractions? Use the abstraction stack from Section 02 in your argument.
08 · Ecosystem

Designing and testing chips on AWS, Google Cloud and Azure

Chip projects need compute in bursts. A verification regression might run ten thousand simulations overnight, and place-and-route of a large block can need hundreds of gigabytes of memory for a day. Then the machines sit idle. Public clouds rent that capacity by the hour, and on AWS you can also rent FPGA boards. This section explains how a cloud design environment is put together, what each provider offers as of November 2026, and how to use it on a student budget.

Before you spend money: a checklist

LicensesCommercial tools need licenses that are valid in the cloud. Check the vendor's cloud terms, or use a vendor cloud offering where licensing is included. Open-source tools need no licenses, which is a big reason courses use them.
Protect the designChip designs are valuable IP. Use a private network, no public IPs on compute, encryption at rest, and remote desktops so data never reaches laptops. Managed workspaces such as Azure's workbench bundle these controls.
Spot interruptionsSpot capacity is much cheaper but can be reclaimed at short notice. Use it for short, restartable simulations. Don't use it for a day-long place-and-route run unless the tool can checkpoint.
Data egressDownloading large waveform files costs money and time. Keep data in the cloud, view waveforms on a remote desktop, and archive old runs to cold object storage.
Right-size machinesSimulation scales with core count. Place-and-route and sign-off are limited by memory and single-thread speed. A single machine shape for everything wastes money on one of the two.
Shut it downAn idle FPGA or high-memory instance still bills by the hour. Set budget alerts and auto-stop rules on day one.

A cloud lab plan for this course

  • Week 5: run Verilator and cocotb tests on every push with a free CI service. No cloud account needed.
  • Week 8: fan the cocotb regression out to a small spot-instance pool (Fig 18) and compare wall-clock time with your laptop.
  • Week 11: build the GEMM accelerator on a cloud VM with AMD's no-cost Vitis HLS and read the synthesis report. This is the latency feedback missing from the local agent setup.
  • Week 12: run the OpenROAD/OpenLane flow in a container on a high-memory VM.
  • Project, optional: deploy on AWS F2 for a few hours and measure real throughput.

All three providers run student or education credit programs (AWS Educate and AWS Academy, Google Cloud education credits, Azure for Students). Amounts and eligibility change, so check the current terms before planning a budget around them.

How this connects to ChipDesignAgent

  • The missing performance signal. Running run_hls_synthesis on a cloud VM with Vitis HLS gives the optimization agent real latency and resource numbers, so the loop can improve speed as well as correctness.
  • Parallel verification. The verification agent can send many testbench variants to a cloud pool instead of running them one at a time.
  • Bigger models when needed. Gemma 4 can run on a cloud GPU VM, or a single agent's model can be switched to a hosted one through CHIP_AGENT_MODEL_<ROLE>, while the code stays in your private network.
  • Industry is heading the same way. In April 2026 Cadence announced its ChipStack AI Super Agent on the Google Cloud Marketplace, integrated with Gemini. Synopsys has shown agentic chip-design workflows for evaluation on Microsoft Discovery.
